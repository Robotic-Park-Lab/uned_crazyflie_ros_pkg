# uned_crazyflie_driver

`ament_python` package with the **two** driver nodes for the Crazyflie swarm — one per kind of robot — plus every Python module that is genuinely common to both.

## Nodes

- **`swarm_driver`** (`swarm_driver.py`, entry point registered in `setup.py`): `CFSwarmDriver`, connects to one or more **physical** Crazyflies via [`cflib`](https://github.com/Robotic-Park-Lab/crazyflie-lib-python) (lab fork). Instantiates one `crazyflie_agent.Crazyflie_ROS2` per drone (`scf=`).
- **`webots_driver`** (`webots_driver.py`): `CrazyflieWebotsDriver`, the flight controller for a **virtual** Crazyflie in Webots. Not a `ros2 run` node — it's loaded per-robot as a `webots_ros2_driver` plugin, referenced by class path from the URDF (`uned_crazyflie_config/resources/crazyflie.urdf`: `<plugin type="uned_crazyflie_driver.webots_driver.CrazyflieWebotsDriver">`), and driven by Webots calling `step()` once per simulation tick.

## Why two classes and not one (design note, 2026-08-22)

The obvious-looking unification — make `CrazyflieWebotsDriver` a thin wrapper that instantiates `Crazyflie_ROS2(..., webots_node=webots_node)` (there was a commented-out line doing exactly this in `webots_driver.py`, from an earlier, abandoned attempt) — was reconsidered from scratch for this pass and rejected, for a concrete reason, not by assumption:

`Crazyflie_ROS2` has no per-tick control loop. Physical Crazyflies fly themselves — Python only relays high-level commands to the onboard firmware via `cflib`'s `high_level_commander` (`take_off()`, `descent()`, `goalpose_callback()`, ... are all gated `if self.physical:` and end in a `scf.cf.high_level_commander.*` call). A Webots Crazyflie has no firmware to relay to: the entire flight controller — GPS/IMU/gyro sampling, the 12-stage cascaded PID chain (position -> velocity -> attitude -> rate), motor mixing, the whole `IPC_controller()` alternative, and the 4 relay-tuning helpers — has to run in Python instead, and it lives entirely in `CrazyflieWebotsDriver.step()` plus `IPC_controller()` and `update_*_relay()`. `Crazyflie_ROS2.virtualCrazyflie()` only ever *initializes* the Webots devices and PID objects (via `webots_bootstrap`, see below) — nothing in `crazyflie_agent.py` ever calls `.update()` on them or drives motors. Reviving the commented-out constructor call would silently produce a Crazyflie that never moves in Webots: `take_off()`/`goalpose_callback()`/etc. would set `self.target_pose` and then do nothing, because the physical-only branch that would act on it is skipped and no equivalent virtual branch exists in that class.

The two classes' formation-control logic also diverges for real, not cosmetically: `CrazyflieWebotsDriver.load_formation_params()`/`distance_gradient_controller()` support Sphere/Cone/Ellipsoid consensus geometries and `ML1`/`ML2`/`ML3` controller variants (via `multi_agent_pkg.lagrange_multipliers`); `Crazyflie_ROS2.load_formation_params()`/`task_formation_distance()` only implements plain distance consensus. Forcing these through one code path would mean picking one feature set and silently dropping the other.

## What actually was unified in this pass

Genuinely identical or near-identical code, extracted so it exists in exactly one place instead of two:

- **`driver_config.py`** -- `resolve_driver_config(config)`: both classes used to re-derive the same set of per-robot flags (`control_mode`, controller type -> IPC/PID, `physical`/`digital_twin`, `communication`/`threshold`, and the `*_enable` flags for `local_pose`/`local_twist`/`data_attitude`/`data_rate`/`data_motor`/`mars_data`/`data`) from `config` in their `__init__`/`init()` -- the physical side by direct dict access (`KeyError` if a key was missing), the Webots side defensively (`"key" in config`, with a fallback). Unified with the defensive style: same result when the keys are present (which they always are in real configs), no crash when they aren't. Fixed one real latent bug along the way: `CrazyflieWebotsDriver.init()` checked `"local_pose" in self.config` before reading `enable`, but then read `self.config['local_pose']['path']` unconditionally right after -- a `KeyError` if `local_pose` were ever fully absent. `resolve_driver_config()` defaults both safely. Deliberately excludes `task` (formation): the point at which each class gates starting formation logic differs enough between the two (`Crazyflie_ROS2` self-gates inline wherever `config['task']['enable']` is checked; `CrazyflieWebotsDriver` gates upfront via `task_config`/`task_onboard`) that unifying it wasn't worth the risk this pass -- left as a candidate for later, noted in `AUDIT.md` (`doc` branch).
- **`sensors.py`** -- `build_laserscan()`: was `Crazyflie_ROS2.publish_laserscan()` and `CrazyflieWebotsDriver.publish_laserscan_data()`, byte-for-byte identical bodies. `agent_removal_marker()`: the "degenerate `LINE_LIST` marker that erases a neighbour's RViz connection line" block, duplicated 4 times across the two files (`Crazyflie_ROS2.disconnected()`/`remove_agent()`, `CrazyflieWebotsDriver.remove_agent()`/`_disconnected()`), all with identical fields.
- **`webots_bootstrap.py`** (pre-existing, unchanged this pass): Webots motor/sensor initialization and the 12 cascaded `PIDController`s -- the real shared "virtual flight hardware" base, called from both `Crazyflie_ROS2.virtualCrazyflie()` and `CrazyflieWebotsDriver.init()`.
- **`agent.py`** / **`cmd_motion.py`** / **`pid_controller.py`** / **`pid_params.py`** (pre-existing, unchanged this pass): `Agent` (neighbour tracking, RViz markers) and `CMD_Motion` are already shared between both drivers; `PIDController` and `apply_controller_params()` likewise. Not the same classes as their namesakes in `uned_crazyflie_missions` -- those are deliberately simpler; see the comments in each file.

`crazyflie_ros2_test.py` (`Crazyflie_ROS2_TEST`) has been deleted: re-confirmed via a repo-wide grep that nothing instantiates it (only its own docstring mentioned the class name), and it wasn't registered as a `console_script`.

## Tests

Real unit tests for the code that is genuinely pure Python with no live ROS/`cflib`/Webots dependency, on top of the standard `ament_copyright`/`ament_flake8`/`ament_pep257` lint tests every package already has:

- **`test_driver_config.py`** (new): `resolve_driver_config()` checked against a real per-robot config block (`uned_crazyflie_config/resources/demo_individual_waypoints_webots.yaml`, `Robots.Robot01`), comparing its output field-by-field against a literal reproduction of *both* the old physical (non-defensive) and old Webots (defensive) derivation logic -- proving the unification changes nothing when the config is complete. Plus: IPC controller type sets the right flags, discrete communication reads the explicit threshold, a fully absent `local_pose` key defaults safely instead of raising (the latent bug above), and an entirely empty config never raises.
- **`test_sensors.py`** (new): `build_laserscan()` orders ranges back/left/front/right/back correctly, saturates above `MAX_RANGE` to infinity, and matches the original angle/range constants; `agent_removal_marker()` is the expected degenerate `LINE_LIST` marker.
- **`test_pid_controller.py`** (`pid_controller.py`): the proportional/integral/derivative response, that `UpperLimit`/`LowerLimit` saturate the output (and that `UpperLimit == 0.0` disables saturation entirely -- real behaviour of the code, not a bug), that the integral term uses the *previous* error rather than the one just set (also real, deliberate behaviour), the event-based trigger (`eval_threshold`) firing on a large enough delta and not re-firing right after, and the relay controller (`rele_update`) switching sign outside its band.
- **`test_pid_params.py`** (`pid_params.py`): `apply_controller_params()` against a fake `set_value` recorder and a fake message -- verifies the right firmware parameter group/suffix per axis type (position continuous vs. event-based, velocity, attitude, rate), and in particular the real firmware quirks that are easy to break by refactoring: the `x`/`y` axes both mapping to the shared `xyVelMax` parameter, and rate axes (`droll`/`dpitch`/`dyaw`) mapping to a firmware parameter name with the leading `d` stripped (`roll_kp`, not `droll_kp`).
- **`test_cmd_motion.py`** (`cmd_motion.py`): `CMD_Motion.ckeck_pose()` (sic -- real typo in the code, left as-is) leaves the pose untouched within its soft limit, only warns between the soft and hard limit, clamps to 85% of `xy_lim` (both signs) once past the hard limit, and never touches the Z axis (out of its scope).

**Deliberately not unit-tested**, and why: `Agent` (creates ROS subscriptions/publishers straight from `__init__`, and reads several fields off a live `parent` driver object -- mocking that faithfully would be more fragile than valuable), `Crazyflie_ROS2`/`CrazyflieWebotsDriver`/`CFSwarmDriver` themselves (full ROS nodes with a real dependency on `cflib`/Webots; testing the wiring meaningfully needs a running simulator or hardware, not a unit test -- though both were smoke-tested by direct instantiation against a real config file plus, for `CrazyflieWebotsDriver`, several `step()` iterations against faked device objects, as part of verifying this pass), and `webots_bootstrap.py` (needs a live Webots `Robot` object to initialize devices against).
